# ADR 0001 — retain the current connector for this milestone; qualify Caddy separately

Status: accepted for the first policy-safety milestone; Caddy adoption remains conditional.

## Context

The roadmap prefers reusing a maintained edge implementation for TLS, reverse proxying, routing and operational behavior. The current OpenWAF connector already owns its transaction lifecycle, hard request limit, structured events and atomic runtime replacement. Replacing it must preserve those contracts.

The released Coraza Caddy module v2.6.2 depends on Caddy v2.11.4 and the legacy embedded CRS v4.25.0 module. OpenWAF uses the split CRS v4.30.0 module. Comparing the default bundles would mix rule-version differences with connector differences.

## Experiment

tools/edgecheck is a separate Go module, requiring Go 1.26. It runs actual local HTTP listeners through both implementations, with identical policy directives generated by gateway.Directives. The candidate reads extracted copies of the exact same Coraza configuration and CRS 4.30.0 files used by OpenWAF; its older bundled CRS is disabled.

The focused 48 cases cover clean GET/JSON, SQLi, JSON XSS, malformed JSON, chunked JSON, scope boundaries, body limits, response intervention and the shell-command coverage observation. Policies include enforcing PL1/PL2, detection and disabled modes. It is not a full Caddy reliability or protocol qualification.

Observed result: 46 matching statuses and two intentional contract differences. OpenWAF returned 413 for oversized requests in detection and disabled modes. The tested unwrapped Caddy integration returned 200 and forwarded them. The original engine 3.8.1 run reproduced the PL1 shell-command miss. After pinning upstream commit 08aa51147300, both connectors block it at PL1; the comparison now requires that behavior.

## Decision

Keep the current connector for this implementation slice. Keep Caddy and its large dependency graph out of the runtime module while evaluating it. Add the comparison to CI and treat new unexplained differences as failures. Do not market or ship two supported production edge implementations.

Before adopting Caddy, build and test the OpenWAF adapter that enforces mode-independent request budgets, exposes structured transaction evidence and policy identity, preserves response behavior, and supports per-application policy activation. Then qualify cancellation, large uploads, streaming, upgrades, HTTP/2, reloads, resource bounds and failure handling. Existing policy, history and scoped-exception logic must remain independent of the edge implementation.

## Consequences

OpenWAF continues to own the connector's correctness and resource limitations in the interim. Automatic certificates and Caddy routing are not yet available in the runtime. The comparison provides a reproducible starting point for the eventual decision; 46/48 matching statuses are not a production-readiness assessment.

Reproduce from tools/edgecheck with `go test -v ./...`. The generated artifacts/edge-comparison.json and edge-comparison-test.log record the local results. See the pinned go.mod/go.sum and upstream [Coraza Caddy source](https://github.com/corazawaf/coraza-caddy) and [Caddy docs](https://caddyserver.com/docs/).
